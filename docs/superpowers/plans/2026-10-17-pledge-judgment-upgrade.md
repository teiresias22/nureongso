# 공약 판정 기준 고도화 계획 (2026-10-17, 검증 반영판)

## 요약

지금 판정 21,336건은 모두 자동 판정이다. 사람이 검수한 것은 0건이다. 이 가운데 공개 규칙과 다르게 나온 판정이 수백 건 있다.
- 공약보다 먼저 나온 발주공고만으로 '진행'이 된 공약 197건
- 재보궐로 당선된 지 넉 달 만에 '미착수'가 된 공약 38건
- 잴 수 없는 유형이 섞였는데 '미착수'가 된 공약 602건

계획은 세 단계로 나뉜다.
1. **재는 장치를 먼저 만든다.** 규칙을 바꾸는 주에는 정기 실행이 근거 버전(snapshot)을 만든 직후에 지난 판으로 판정을 한 번 돌린다. 이렇게 그 주에 쌓인 입력 변화를 먼저 털어 낸 뒤 새 판을 적용한다. 그러면 이력의 '판정 기준 변경'은 규칙 변경만 가리키고, 출처 기록 변화는 'source'로 따로 남는다. 여기에 다음 셋을 더한다.
   - 쓰기 없는 전이표(`decide --diff`). 지난 판과 새 판을 같은 스냅숏에서 비교한다.
   - 판정 분기 픽스처
   - 사실만 적은 정답 표본
2. **틀린 판정을 줄인다.**
   - 규칙 묶음 R1은 공개 문구와 다르게 돌던 코드를 고친다. 대상은 근거 날짜 조건, 사람별 임기 시작일, 당선 여부, 입법은 국회의원만, 철회 법안 제외, 인물 카드 집계(member_stats)다.
   - 규칙 묶음 R2는 소유자 결정이 필요한 것을 다룬다. 섞인 유형, 임기 첫해 발주, 취임일 당일 공포 조례다.
3. **판단불가는 원칙 안에서만 줄인다.** 개수를 줄이기보다 사유를 바로 적는 것이 먼저다. 대조 입력은 놓침률을 잰 뒤에만 넓힌다.

사람은 판정을 고치지 않는다. 근거에 검수 표시(새 칸 `pledge_evidence.review`)만 단다. 판정은 늘 규칙표가 낸다.

새로 더하는 판정 규칙과 장치는 LLM 을 부르지 않는다. 다만 브랜치를 병합하면(P0-0) 정기 실행에서 증분 재대조·quote·repro 가 켜진다. 그래서 매주 LLM 호출이 생기고, 병합 뒤 첫 주에는 수백 회로 추정한다(P0-0). 새 출처는 들이지 않는다. 쓰기는 규칙 묶음 하나에 약 3.3천 행 이하다.

전제가 하나 있다. 정기 `evidence.yml` 은 지금 master 코드로 돈다. 작업 브랜치는 master 보다 21커밋 앞서 있고, 운영 트리거는 이미 켜져 있다. 그래서 병합 전에 생기는 판정 변화는 이력에 `rule='manual'` 로 남는다. 사람이 SQL 로 고친 것과 같은 표시다(부록 A1·A2).

## 1. 목표와 비목표

### 목표
1. **규칙 변경을 정확히 기록한다.** 규칙 때문에 바뀐 판정은 이력에 'rule'(판정 기준 변경)로만 남긴다. 기록이 바뀌어 달라진 판정은 'evidence'·'source'·'elapsed'·'input'으로 남긴다. 화면, 메일, `/rules` 가 같은 말을 하게 한다.
2. **규칙을 바꾸기 전에 숫자로 잰다.** 쓰기 없는 전이표, 판정 분기 픽스처, 불변식, 사실 라벨 정답 표본을 쓴다.
3. **과대 판정을 먼저 걷어 낸다.** 대상은 약속보다 먼저 나온 기록, 취임 전 기록, 잘못 붙은 연결로 만들어진 완료·진행이다.
4. **'미착수'를 단정할 근거를 갖춘다.** 미착수는 이 서비스에서 유일한 부정 판정이다. 판정 기준을 그 사람의 실제 임기와 잴 수 있는 유형에 맞추고, 놓침률을 잰다.
5. **사람 검수를 실제로 쓴다.** 첫 대상은 '완료' 35건 전수다. 사람은 근거에 review 표시만 단다. 판정은 그 근거로 규칙표가 다시 낸다. 사람이 확인한 판정은 모든 화면과 메일에서 '사람 확인'으로 보인다.
6. **작게 배포한다.** 작업 하나가 커밋 하나다. 운영 적용은 묶음 단위로 한다. 묶음마다 전이표와 되돌리는 법이 있다.

### 비목표 (원칙상 하지 않는다)
- 의견·평점·댓글을 싣지 않는다. 외부 기관 이행 등급, 단체장 자체 이행 평가, 정치자금 기부내역·병역·납세·전과도 싣지 않는다(README '싣지 않는 것', `web/src/app/rules/page.tsx` 6·20번).
- **LLM 이 판정하지 않는다.** score, why 문자열, quote_ok 는 판정 조건이 아니다. score 는 검수 순서에만 쓴다. quote_ok 는 소유자 결정 E에 따라 표시만 한다.
- **판단불가 개수를 줄이는 것 자체를 목표로 두지 않는다.** 판단불가 19,841건 가운데 원칙상 판정 대상이 아닌 몫이 크다(§4 M1). 고치는 것은 사유 문구다.
- 근거가 없는 공약을 미착수로 적지 않는다. 발주 공고만으로 '완료'를 주지 않는다. 공동발의와 표결 찬성은 근거로 쓰지 않는다.
- 판정 상태 4종(완료·진행·미착수·판단불가, `schema.sql:189` check)을 늘리지 않는다. 새 사유는 note 로 나눈다.
- 이번 계획에서는 새 출처(20·21대 법안, 용역·계약정보, 입법예고, 지방재정365, CLIK)를 들이지 않는다. 나중에 들일 때 지킬 규칙만 Phase 5에 적는다.
- 웹 지표 대시보드, 검수 DB 표, 스테이징 DB 는 만들지 않는다.

## 3. 단계별 작업

### 3.0 공통: 규칙 배포 절차 R (Phase 0 이후 판정 규칙을 바꾸는 모든 작업)

배포는 **묶음(release) 단위**로 한다. 묶음 하나가 규칙 판 하나이고, `/rules` 변경 기록의 한 줄이다. 작업 하나는 커밋 하나이고, 혼자서도 검증과 배포가 된다. 묶는 이유는 두 가지다. 이력에서 공약마다 'rule'이 여러 번 찍히지 않게 하고, 운영 단계를 줄인다.

1. **커밋마다 같이 넣는 것**
   - JUDGED 변경
   - `collector/decide_check.py` 기대값 변경. 이 diff 가 곧 규칙 변경의 명세다
   - 새 note 의 `NOTE_LABEL`
   - `/rules` 표 행
   - `/rules#changes` 의 묶음 줄. 판 이름은 커밋마다 지금 `RULE_VERSION` 으로 고친다. 계약 시험 (b)가 빠뜨림을 막는다
   - 커밋 본문에 `decide --diff --base <직전 커밋>` 전이표
2. **로컬 검증** (모두 통과해야 한다)
   - `dotenvx run -- .venv/bin/python judge.py decide --diff --base <직전 커밋>`(SELECT 만). 같은 스냅숏에서 지난 JUDGED 와 지금 JUDGED 를 비교한 순수 규칙 전이다. 이 값이 작업의 '기대 전이'와 맞아야 한다
   - `decide_check.py`
   - collector 테스트(계약 시험과 SQL 변환 시험 포함)
   - `npm run lint && npm run build`
3. **master 병합은 일요일에 한다.**
   - Vercel 이 master 를 바로 배포하므로 **웹(새 라벨)이 DB 보다 먼저** 나간다. `db.ts:124` 의 `?? note` 때문에 라벨이 없으면 코드 글자가 그대로 보인다.
   - `/m/*`·`/`·`/stats`·`/compare`·`/my` 는 CDN 캐시가 하루에 stale-while-revalidate 하루가 더 붙는다(`next.config.ts:35-37`). 그래서 월요일 적용 뒤에도 최대 이틀은 옛 판정이 보일 수 있다. 평소 수집 반영과 같은 지연이라 캐시를 따로 비우지 않는다. 재배포로 비우면 크롤러가 다시 그리면서 Active CPU 를 쓴다(추정).
4. **월요일 정기 `evidence.yml` 의 '규칙 판 적용' 단계(T0.1)**
   - 이 단계는 수집·대조·근거 버전(snapshot) **뒤**, '판정 다시 적용' **앞**에 둔다.
   - 동작 순서:
     - `rule-prev` 가 진행 중인 ingest 가 없는지 확인한다. 진행 중이면 최대 60분 기다린다.
     - 지난 판 커밋을 worktree 로 꺼내 `decide` 를 한 번 돌린다. 한 주 동안 쌓인 입력 변화는 이때 'evidence'·'source'·'elapsed'·'input'으로 찍힌다. snapshot 이 바로 앞에서 돌았으므로 출처 기록 변화는 'source'로 바르게 남는다.
     - 이어서 새 판 `decide --rule` 을 돌린다. 이번에 바뀐 판정은 모두 'rule'로 찍힌다.
     - 그다음 평소의 '판정 다시 적용'이 돈다. 기대값은 0행이다.
   - 이 순서가 필요한 이유: 법안 처리결과와 당선 기록은 매일·매주 바뀐다(`ingest.yml` 매일, `nec.yml` 화요일). 그런데 판정은 주 1회만 돈다. 털어 내지 않으면 그 차이가 'rule'로 섞인다.
   - ingest 를 확인하는 이유: `ingest.yml`(그룹 ingest)과 `evidence.yml`(그룹 evidence)은 동시 실행 그룹이 달라 겹쳐 돈다. 10-12에는 ingest 가 22:40~01:40Z 에 돌았고, 그 안인 23:32~23:45Z 에 evidence 가 돌았다(A17). 두 워크플로를 한 그룹에 넣으면 대기 실행이 취소되는 함정이 있어서 그렇게 하지 않는다(CLAUDE.md).
   - 급하면 `evidence.yml` 을 workflow_dispatch 로 돌린다. 이때 수집과 증분 재대조도 같이 돌아서 LLM 호출이 생긴다(추정 수백 회 이내, P0-0).
5. **확인**
   - 요약에 찍힌 그 실행의 'rule 전이표'를 커밋 본문 전이표의 묶음 합계와 칸마다 비교한다. 차이는 칸마다 ±10건 또는 ±5% 이내여야 한다. 그 주의 입력 변화가 규칙에 걸리는 행을 바꾸기 때문이다. 넘으면 그 칸 표본을 본다.
   - 불변식(§4)이 기대값과 같아야 한다.
   - 화면에서 `/pledge` 표본 5건을 본다. `/m` 한 명은 CDN 캐시 때문에 화요일 이후에 본다.
6. **되돌리기**
   - `git revert` 하고 일요일에 병합한다. 다음 실행의 같은 단계가 'rule'로 되돌린다.
   - 이력 행은 사실 기록이라 지우지 않는다. `/rules#changes` 에 '되돌림'을 적는다.

**이력·메일·화면에 주는 영향 (모든 규칙 작업 공통)**
- 바뀐 행만 고르고 바뀐 행만 쓴다(T0.2 뒤).
- 주간 메일은 `reason <> 'rule'` 이면서 상태가 실제로 바뀐 줄만 싣는다(`schema.sql:1221`). 그래서 규칙 변경은 메일로 나가지 않는다. 메일은 지금 보류 상태이기도 하다.
- `/pledge` 타임라인에는 '판정 A → B · 판정 기준 변경' 또는 '판정 사유 바뀜(판단불가 유지) · 판정 기준 변경'으로 **보인다**(`timeline.ts`). `/rules` 3번이 약속한 '따로 표시'를 지키는 방식이므로 숨기지 않는다.
- 인물 페이지는 T0.4 부터 '기준 변경'으로 따로 적는다.

## 7. 하지 않기로 한 대안과 이유

| 대안 | 하지 않는 이유 |
|---|---|
| score 문턱(예: ≥ 0.7)을 판정 조건으로 | 시뮬레이션 d3 에서 완료 34→29·진행 487→440 인데 **미착수가 735→764 로 는다**(현황 rules). 명백한 오탐이 0.8~0.9 를 받는 등 보정도 약하다. 'LLM 은 잇기만' 원칙과 부딪친다. 검수 순서에만 쓴다 |
| quote_ok 를 완료 조건으로 | 소유자 결정 E. 법안에만 해당하고 측정값이 아직 0이다. 구절을 옮겼는지만 재고 연결이 맞는지는 재지 않는다 |
| 조례·발주에 quote_ok 를 남기고 웹에서만 감추기 | 공개 표에 확인하지 않은 true 가 687행 남는다. 덩어리를 지우면 쓰기도 0이다(T0.0) |
| 기준선 21,336행의 rule 을 UPDATE 로 채우기 | 첫 변경만 고친다. 낡은 직전 줄 문제는 남고, 21,336행을 다시 쓴다. 실행 맥락 방식이 쓰기 0으로 둘 다 막는다 |
| 판 해시 비교 유지 + 병합 직후 수동 `decide` | 한 주 동안 쌓인 입력 변화가 'rule'로 섞이고, 1인 운영에 수동 단계가 남는다 |
| 잡 맨 앞에 `--rule-if-new` 만(털어 내기 없이), 또는 털어 내기를 snapshot 앞에 | 앞의 것은 매일 바뀌는 법안 처리결과·당선 기록을 'rule'로 섞는다. 뒤의 것은 그 주 출처 변화를 'source' 대신 'input'으로 남긴다. snapshot 뒤 worktree 털어 내기가 둘 다 막는다 |
| evidence 를 ingest 동시 실행 그룹에 넣기 | 그룹은 실행 하나 + 대기 하나라서 대기 실행이 취소된다(CLAUDE.md). ingest 확인 후 기다리기로 대신한다 |
| `decide --check`(INSERT+롤백) 유지 | 매주 쓰기와 트리거가 돈다. SELECT 전이표가 같은 일을 더 자세히 한다 |
| 판 해시에서 SQL 주석 빼기 | 문자열 안의 `--` 를 지울 위험이 있다. T0.1 뒤에는 주석만 바꾼 판이 0행을 쓰고 끝나 해가 없다 |
| 판 이름을 test 에 박아 두기(`== '9df1c6e9'`) | 규칙 커밋마다 깨진다. 판과 변경 기록이 맞는지는 계약 시험 (b)가 보고, 나누기가 맞는지는 decide_check 가 본다 |
| why 막연함(vague) 거르기를 법안·조례에도 | 놓치는 쪽으로만 틀리고, 놓친 연결은 그대로 미착수가 된다. 검수 순서에만 쓴다 |
| 일부개정 조례는 완료 대신 진행으로 | 일부개정으로 공약을 이행하는 경우가 있다(7145). 법안의 일부개정 가결과 일관성이 깨진다. 완료 전수 검수가 더 싸고 정확하다 |
